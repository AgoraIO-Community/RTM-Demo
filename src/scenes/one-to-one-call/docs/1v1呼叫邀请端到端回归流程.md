# 1V1 呼叫邀请端到端回归流程

更新日期：2026-10-19

回归分别核对邀请状态、App 展示与 RTC 媒体。状态依据见[状态流转与时序](./1v1呼叫邀请状态流转与时序.md)，接口依据见[功能与 RTM 函数映射](./1v1呼叫邀请功能与-rtm-函数映射.md)。

App 回到空闲后，原邀请仍保留接受、拒绝、取消或失败终态，不返回 `IDLE(0)` 或 `IDLE(10)`。

## 1. 验证层次与命令

| 层次 | 验证内容 | 边界 |
| --- | --- | --- |
| 协议/插件/邀请单测 | SDK 自动路由、四类信令、角色枚举、重试、截止、ACK、错误与实例隔离 | 不依赖真实 Agora 服务或 RTC |
| App 集成/组件测试 | 多来电、单通媒体名额、昵称、媒体截止、资源清理与交互 | 底层 SDK 使用可驱动替身 |
| 无头双页面 E2E | 邀请、接听、拒绝、取消、到期、静音、挂断、再次发起和数据流 | 验证页面间协议与交互，不证明真实音频 |
| 真实服务联调 | USER 发布、Token、网络、RTC、采集、播放与设备恢复 | 记录指定设备和网络中的实际结果 |

## 2. 两种接入路径验收

### 2.1 客户 App 直接使用插件

复制完整 [invitation/](../invitation/index.ts) 目录，以 App 已登录的 SDK Client 验证公共入口；不引入 Demo 的 CallRtm、页面 Session、React 或 RTC：

```ts
import { Invitation } from './invitation';

const invitations = new Invitation(rtmClient, {
  userId,
  onIncomingInvitationsChanged: items => renderIncoming(items),
  onCallerStateChanged: event => recordCaller(event),
  onCalleeStateChanged: event => recordCallee(event),
});
```

| 场景 | 预期 |
| --- | --- |
| 已登录 Client 安装 | 不要求 App 实现 port 或手工分发，自动注册自己的 message/linkState listener |
| userId | 由 App 明确传入且与登录 UID 一致，不读取不存在的 SDK UID getter |
| 默认初始连接 | 按 connected 使用已登录 Client |
| login 前安装 | 设置 initialLinkState=disconnected；在真实连接事件前不发起有效呼出 |
| USER 发布 | SDK publish 使用目标 UID、四种邀请 customType、channelType=USER、storeInHistory=false |
| 同一 Client 重复安装 | 不允许同时重复安装，避免重复消费与重复发布 |
| App 其他 customType | App 原有 SDK listener 仍收到自己的业务消息，插件不独占 message 事件 |
| extra 透传 | 邀请体内字符串经 remoteExtra 暴露，不被当作独立业务 customType |
| 独立业务消息 | 使用 App 自己的 customType/listener，不混入 CALL_KIT 信令 |
| dispose | 仅停止所属邀请和移除自己的 listener，不 login/logout、不移除 App listener |
| 卸载后重装 | 相同 Client 可重新安装，旧插件不继续消费或重发 |
| SDK logout 与重新登录 | 先 dispose 插件再 logout；SDK 清理监听后，重登须重新安装插件 |
| STREAM 独立性 | 仅 STREAM 状态变化不改变 USER 邀请连接判断 |
| 目录独立性 | invitation/ 内部依赖完整，可复制到已有 SDK App，无 Demo 场景或媒体依赖 |

### 2.2 Demo 通过 CallRtm 操作邀请

Demo 使用 [rtm.ts](../rtm.ts) 提供的用户业务函数，SDK 事件和页面已登录端口由场景 Session 接入：

```ts
const rtm = new CallRtm({ userId, session });
const outgoing = rtm.createOutgoingInvitation(targetUid, 'app-defined-data');
outgoing.subscribe(() => renderInvitation(outgoing.getSnapshot()));
await rtm.sendCallInvitation(outgoing.callId);
```

| 场景 | 预期 |
| --- | --- |
| 构造 | session 提供 getCallPort/getCurrentLinkState；不由 App 媒体层创建插件或传入 publish 端口 |
| 创建邀请 | 返回 RtmInvitation，只含只读 callId、getSnapshot、subscribe |
| 业务操作 | sendCallInvitation/acceptCallInvitation/refuseCallInvitation/cancelCallInvitation 按 callId 操作 |
| 句柄隔离 | 句柄没有 start/accept/refuse/cancel，不可绕过场景 RTM 业务入口 |
| 状态与集合 | getInvitation/getSnapshot 返回同一邀请的只读视图，callerInvitations/incomingInvitations 保持状态与截止 |
| 事件 | incomingInvitation 返回只读句柄，角色状态/集合/错误事件不暴露可操作插件对象 |
| SDK 分发 | OneToOneCallScene 将 message/linkState 直接分发到 CallRtm；AppCallController 不解析原始信令 |
| trace | 发布通过 AppCallRtmSession 已登录端口，保留真实 RTM API/Event |
| App 边界 | AppCallController 只依赖 rtm.ts 的信令接口，RTC、昵称、互拨和单通媒体策略仍留在 App |
| 清理 | CallRtm 停止邀请，App 清理媒体，页面 Session 另行尽力 logout，旧邀请不影响新资源 |

## 3. 双页面基础流程

### 3.1 正常接听与音频

1. A、B 打开 `/social/one-to-one-call`，等待 CONNECTED，确认各自呼叫 ID 不同。
2. A 输入 B 的 ID 发起邀请。Caller 从 `IDLE(0)` 进入 `SENT_TO_CALLEE(1)`；发送中无接听倒计时，INVITE publish resolve 后进入 `RECEIVED_BY_CALLEE(2)`，从完整默认 30 秒开始等待。
3. B 首次消费 INVITE，Callee 从 `IDLE(10)` 进入 `INVITATION_RECEIVED(11)`，从本地首次消费时刻开始自己的窗口。
4. B 接听并发布 accepted，在途仍为 `INVITATION_RECEIVED(11)`；SDK publish resolve 后进入 `ACCEPT_SENT_TO_CALLER(12)`，保持原截止。
5. A 有效消费 accepted，`RECEIVED_BY_CALLEE(2) → ACCEPTED_BY_CALLEE(3)`，发送同 customType 的 ack。B 有效消费后 `ACCEPT_SENT_TO_CALLER(12) → ACCEPTED(13)`。
6. 两端 App 各自观察接受终态才建立媒体，加入相同派生 RTC 频道；本地已连接且目标加入后展示音频通话。
7. 静音/恢复只操作本地 RTC 麦克风，不增加邀请信令。
8. 一方挂断退出 RTC，已连接对端观察目标离开并结束 App 媒体。邀请仍为 `ACCEPTED_BY_CALLEE(3)` 与 `ACCEPTED(13)`。
9. 不收起结果直接再次呼叫，确认新 callId、新实例与新媒体不受旧资源清理影响。
10. 数据流区分 accepted/ack，且只包含 RTM API/Event，不出现媒体控制信令或 RTC 节点。

### 3.2 拒绝、取消与无人应答

1. Callee 拒绝先提交 `REFUSED(14)` 再通知，Caller 有效消费 REFUSE 后为 `REFUSED_BY_CALLEE(4)`。
2. Caller 取消先提交 `CANCELED(5)` 再通知，Callee 有效消费 CANCEL 后为 `CANCELED_BY_CALLER(15)`。
3. 无人处理时，Caller 从 publish resolve 起等待，本端正常时最终为 `FAILURE(6)`、reason=PEER_NO_RESPONSE；Callee 从首次消费起最终为 `FAILURE(16)`、reason=INVITATION_EXPIRE。
4. 两端不要求同时到期；旧信令不复活终态，再次邀请使用新 callId。

### 3.3 多来电与互拨

1. Caller A、Caller C 同时邀请 Callee B，B 的来电集合保留两项，独立展示对端与截止。
2. B 按条拒绝，仅对应项进入 `REFUSED(14)` 并移除；另一项保持原 `INVITATION_RECEIVED(11)` 和截止。
3. 接听其中一项时，App 预留单通媒体名额，其余来电继续计时、可拒绝；释放名额后可接听仍有效的项。
4. A、B 同时互拨时，Demo App 固定保留字典序较小 callId，取消较大呼出或拒绝较大来电。不同邀请不改绑对象。

## 4. 纯信令联调用例

使用可控制 resolve/reject 的 RTM 替身与假时钟，记录发布次数、customType、完整 payload、sequence、截止及失败证据。邀请单测不注入 RTC、App ID 或 React。

| 场景 | 预期 |
| --- | --- |
| 普通 UID 与最小依赖 | alice/bob 可创建并协作，无 Demo UID 前缀或 RTC 依赖 |
| extra 省略/透传 | 缺省空串，任意 App 字符串原样保留；重试 callId/extra 相同 |
| 默认重试全部失败 | 首次加两次、间隔 2 秒；耗尽立即 `SENT_TO_CALLEE(1) → FAILURE(6)`，trigger=RETRY_EXHAUSTED |
| 首次失败后成功 | 停止 INVITE 重发，`SENT_TO_CALLEE(1) → RECEIVED_BY_CALLEE(2)`，从成功时刻开启完整 Caller 等待 |
| 自定义次数/零重试 | 严格遵守 maxRetries，发送总截止不延长 |
| INVITE 永久 pending | 总截止使 `SENT_TO_CALLEE(1) → FAILURE(6)`，SEND_TIMEOUT；迟到结果不复活 |
| 总截止先于重试耗尽 | 不执行超期重试，不重新开启发送窗口 |
| 起始未连接 | 不发布 INVITE，最终为 `FAILURE(6)`、LOCAL_NETWORK_ERROR |
| INVITE 成功后收到 accepted/REFUSE | 先提交 `RECEIVED_BY_CALLEE(2)`；匹配本次 callId 和对端 UID 的响应再提交 `ACCEPTED_BY_CALLEE(3)` 或 `REFUSED_BY_CALLEE(4)` |
| 非等待响应阶段收到 accepted/REFUSE | 按当前状态直接忽略，不改变后续邀请结果 |
| accepted 发布在途 | 保持 `INVITATION_RECEIVED(11)`、publishing=true，重复操作不并发发布 |
| accepted 发布失败 | 仍有效则保持 `INVITATION_RECEIVED(11)`，operationError 含原错，解除占用后可再次操作 |
| 接听失败后无人操作 | 原截止为 `FAILURE(16)`、INVITATION_EXPIRE，不自动重发 |
| accepted pending 到期 | `INVITATION_RECEIVED(11) → FAILURE(16)`、INVITATION_EXPIRE，操作等待有界 |
| 接听发布中收到取消 | 立即 `CANCELED_BY_CALLER(15)`，迟到 publish 结果/ACK 无效 |
| Caller 先取消再到 accepted | 保留 `CANCELED(5)`，不回 ACK，不启动本邀请媒体 |
| REFUSE/CANCEL 通知错误 | 先提交的 `REFUSED(14)`/`CANCELED(5)` 不回滚，错误独立报告 |
| accepted 成功后收到 ACK | 先提交 `ACCEPT_SENT_TO_CALLER(12)`；有效 ACK 使其进入 `ACCEPTED(13)`，其他阶段的 ACK 直接忽略 |
| 未接听就收到 ACK | 保持 `INVITATION_RECEIVED(11)`，不能直接接受 |
| ACK 失败、缺失或 pending | Caller 保留 `ACCEPTED_BY_CALLEE(3)`，Callee 原截止为 `FAILURE(16)`、ACCEPT_ACK_TIMEOUT |
| 重复 accepted/ACK | 有限窗口内幂等补 ACK，不重复状态通知，不恢复其他终态 |
| 重复 INVITE | 保持同一实例、排序、extra 和原截止 |
| CANCEL 早于 INVITE | 记录 callId/publisher，抑制随后同一邀请 |
| 相同 callId 不同 publisher | 不改写、不重绑已有实例 |
| 多来电隔离 | 一项变化不影响其他项，`ACCEPT_SENT_TO_CALLER(12)` 仍保留在待处理集合 |
| 终态保留 | 接受/拒绝/取消/失败后不返回 `IDLE(0)` 或 `IDLE(10)`，重复信令无复活 |
| stop/dispose | 未终结 Caller/Callee 分别为 `FAILURE(6)`/`FAILURE(16)`、STOPPED；之后不回调或重发 |

## 5. 时间、恢复与归因

1. 空闲 3 秒后拨号，INVITE pending 3 秒，发送中不显示 33 秒；成功首帧为默认完整 30 秒。
2. Callee 首次接收第 29 秒接听，accepted 成功后为 `ACCEPT_SENT_TO_CALLER(12)`，应仅剩约 1 秒，不重新获得 30 秒。
3. 直接将系统时间前移 45 秒而不执行 timer，再触发操作、消息、resolve/reject、重试或 checkDeadlines，均先按原截止终结。
4. now 等于或超过 endTs 都无效；最后 1ms 的有效本端操作不保证对端处理时仍有效。
5. 恢复尚未到期时按 endTs-now 显示，重试次数与发送总截止不变，不集中补发错过的 timer。
6. 验证恢复可见、pageshow、focus、RTM 恢复连接及普通消息入口的重检。冻结期间不能执行 JavaScript，不要求睡眠中的截止瞬间通知。
7. 临时断连不刷新窗口，彻底 failed 使未终结邀请进入 `FAILURE(6)` 或 `FAILURE(16)`，已接受邀请不变。

| 证据 | 归因断言 |
| --- | --- |
| SDK `-11033` 明确离线 | reason=PEER_OFFLINE，保留原始 code/message |
| connected 且 SDK `-11026` | reason=PUBLISH_TIMEOUT，不推断对端离线 |
| connected 且普通发布错误 | reason=PUBLISH_FAILED |
| 失败时 reconnecting，之后恢复 | reason=LOCAL_NETWORK_ERROR，linkStateAtFailure 保留 reconnecting |
| 次数耗尽先到 | trigger=RETRY_EXHAUSTED，立即终结 |
| 发送总截止且当前调用 pending | reason/trigger=SEND_TIMEOUT，不伪造 SDK 错误 |
| Caller `RECEIVED_BY_CALLEE(2)` 到期、本端正常 | `FAILURE(6)`、PEER_NO_RESPONSE、INVITATION_TIMEOUT |
| Callee `INVITATION_RECEIVED(11)`/`ACCEPT_SENT_TO_CALLER(12)` 到期 | 均为 `FAILURE(16)`，分别 INVITATION_EXPIRE/ACCEPT_ACK_TIMEOUT |

## 6. 回调与资源隔离

1. 直接使用插件时，Caller 在 start 前注册 stateChanged；Callee 在 incomingInvitation 中注册可观察首个 `INVITATION_RECEIVED(11)`，直接 accept/refuse 也有效。Demo 由 CallRtm 角色事件提供状态通知，句柄只用于读快照与订阅。
2. onCallerStateChanged/callerStateChanged 与 onCalleeStateChanged/calleeStateChanged 来自真实提交；onIncomingInvitationsChanged 返回完整待处理数组。
3. callId、role、对端 UID 固定，sequence 单调递增，previousState/state 与快照一致。
4. 监听抛错、异步失败或重入取消不阻断其他监听，不破坏事件顺序。
5. 晚注册读取快照；退订不结束邀请，收起 App 提示不擦除终态。
6. alpha 的 RTC leave/join/采集仍 pending 时结束媒体并创建 beta；旧结果、轨道或错误不能覆盖 beta。
7. 旧邀请结束不 logout 页面 Client；插件 dispose 后推进时钟或注入消息，不复活实例，也不移除其他 App listener。

## 7. App 媒体与页面

| 场景 | 预期 |
| --- | --- |
| Caller `ACCEPTED_BY_CALLEE(3)` / Callee `ACCEPTED(13)` 前 | 不为该邀请建立媒体，`ACCEPT_SENT_TO_CALLER(12)` 还不够 |
| 接受终态后 | App 启动独立媒体，默认 15 秒截止包含 join |
| 本地已连接且目标加入 | 展示音频通话，不要求目标已发布麦克风 |
| ACK 丢失 | 允许 Caller `ACCEPTED_BY_CALLEE(3)`、Callee `FAILURE(16)`，媒体按自身截止结束 |
| RTC join 失败/pending | App 报媒体失败/超时，不改邀请接受终态 |
| 采集或发布失败 | 保留收听和重试，不改邀请状态 |
| 静音/挂断/目标离开 | 仅操作媒体；邀请仍保留 `ACCEPTED_BY_CALLEE(3)`/`ACCEPTED(13)` |
| RTM 短暂重连、RTC 正常 | 已建立音频继续，可本地挂断 |

数据流按 callId 关联 RTM API/Event，ACCEPT 摘要区分 type=accepted/type=ack，不展示 extra 正文。先记录 message EVENT，再补消费结果；失败或忽略消息不冒充成功，RTC 不进入数据流。

场景导航整页加载，每页只有一个当前场景 Client。验证 pagehide、Strict Mode、登录失败重试与浏览器历史返回：旧邀请/媒体幂等释放，同页重试复用 Client，真正离页卸载插件并尽力 logout。刷新可保留 Tab 呼叫 ID，不恢复旧邀请。

## 8. 真实服务人工验收

使用有效 App ID、所需外部 Token、可信 HTTPS 与两台设备或独立标签页。项目不生成 Token、不接收 App Certificate。真实音频联调须戴耳机。

1. 执行 `./start-demo.sh --https`，让设备信任本地 CA，分别进入呼叫场景。
2. 交换呼叫 ID，核对 INVITE → accepted → ack 与完整角色状态；确认接收参数 remoteExtra 符合 App 编解码约定。
3. 确认真正加入同一 RTC 频道、双方可听；验证静音、恢复和拒绝权限后的麦克风重试。
4. 验证拒绝、取消、无人应答、多来电、同时互拨及新 callId。
5. 控制网络验证重试、SDK 发布超时、明确离线与本地断连，记录原错和失败时连接证据。
6. 验证接近截止接听、后台/睡眠超过 30 秒后恢复，首个检查不能新增完整窗口。
7. 验证 ACK 缺失、join 失败、对端未加入的媒体超时，以及连接后的 RTC 远端离开。
8. 结束后立即再次呼叫，确认不受旧清理影响；RTM 短暂重连时音频继续并可挂断。
9. 验证独立 App customType 与邀请同时工作，卸载插件后 App 原 listener 仍有效。
10. 刷新、关闭或离开场景后确认本地媒体释放。卸载期异步通知与 logout 不保证完成，对端依靠自身截止或 RTC 事件收敛。

记录版本、SDK 版本、设备、网络、配置、UID、callId、截止、状态事件及错误证据，分别标注自动化结果和真实链路实测项。未执行真实服务验收时明确保留该验证范围。
